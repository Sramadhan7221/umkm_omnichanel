# CLAUDE.md — umkm_omni_web

Memori jangka panjang untuk semua sesi kerja di project ini. Baca file ini di awal setiap sesi sebelum mulai coding.

## Konteks Proyek

`umkm_omni_web` adalah sistem omnichannel MSME (Shopee, GrabFood, GoFood, TikTok Shop) yang saat ini sudah punya Order Inbox, inventory sync, fee reconciliation, dan expense tracking manual. Project sedang menambahkan modul akuntansi double-entry penuh berbasis SAK EMKM (Chart of Accounts, jurnal otomatis, HPP, PPh Final, Neraca) dan modul POS offline untuk toko fisik, menggantikan financial engine ringkas yang ada sekarang. Sumber requirement: `docs/Analisis_Kebutuhan_Modul_Akuntansi_POS.pdf` (v2, 12 Agustus 2026).

## Keputusan Scope yang Sudah Final (jangan tanya ulang, jangan asumsikan beda)

1. **Double-entry MENGGANTIKAN laporan lama, bukan berdampingan.** `get_income_statement()` dan `get_cash_flow()` di `financial_service.py` akan di-deprecate setelah engine berbasis saldo akun (Epic F) tervalidasi. `financial.py` (router) dan `financial.html` diarahkan ke engine baru — jangan pertahankan sebagai mode kedua/opsional.
2. **Tidak ada backfill jurnal retroaktif.** Aplikasi belum go-live, start from zero. Database demo (OmniOrder, Settlement yang sudah ada) boleh di-reset sebelum Epic A/B mulai dipakai. Jangan bangun job migrasi data historis.
3. **Master Barang adalah single source of truth harga di semua kanal, termasuk POS Kasir.** Harga jual + HPP ditentukan owner di Master Barang, lalu disinkronkan keluar ke tiap platform. Kasir POS tidak boleh input/override harga manual — selalu ambil read-only dari Master Barang.
4. **Kas fisik terpisah per outlet, tapi Neraca tampilkan baris konsolidasi.** Tiap outlet fisik punya saldo kas sendiri (akun 1111 Kas di Tangan, `is_outlet_scoped=true`), tapi Neraca tetap menjumlahkan semua outlet jadi satu baris, dengan breakdown per outlet di drill-down.

## Konvensi Kode yang Sudah Ada di Project

Hasil observasi `app/models/db_models.py`, `app/models/canonical.py`, `app/mock_adapters/base.py`, `app/services/*.py`:

- **Model SQLAlchemy** (`app/models/db_models.py`): satu file datar berisi semua model, dikelompokkan per modul dengan comment-block header (mis. `# --- Inventory Sync (Fase N) --- #`). Primary key business-meaningful dipakai sebagai string PK bila memang natural (`OmniOrder.platform_order_id`, `Product.sku`, `Platform.code`) — bukan selalu autoincrement id. Model baru (`Account`, `Outlet`, `JournalEntry`, `TransactionMappingRule`) ikuti pola ini: tambahkan di file yang sama dengan comment-block header baru, bukan file terpisah per model.
- **Canonical layer** (`app/models/canonical.py`): semua enum kanonik (`Channel`, `FulfillmentType`, `OrderStatus`, `FeeCategory`) didefinisikan sebagai `str, Enum` di sini, dan seluruh sistem downstream (services, routers) hanya boleh bergantung pada tipe canonical ini — jangan sentuh raw platform payload di luar `mock_adapters/`. Menambah `Channel.OFFLINE_POS` (Epic C) dan pemetaan channel → kode akun pendapatan (Epic A) masuk ke file ini.
- **PlatformAdapter pattern** (`app/mock_adapters/base.py`): abstract base class dengan method abstrak (`authenticate`, `fetch_orders`, `normalize_order`, `push_stock_update`, `parse_webhook`, `parse_settlement`). Method baru `push_price_update(sku, price, cogs_price)` (Epic D) harus ditambahkan sebagai abstractmethod di `base.py`, lalu diimplementasikan di keempat mock adapter (`mock_shopee.py`, `mock_grabfood.py`, `mock_gofood.py`, `mock_tiktokshop.py`) mengikuti pola persis `push_stock_update` (return `SyncResult`).
- **Services** (`app/services/*.py`): fungsi-fungsi flat (bukan class) yang menerima `db: Session` sebagai parameter pertama, docstring modul di atas menjelaskan fase/konteks bisnis. Ikuti pola ini untuk service baru (`chart_of_accounts_service.py`, `outlet_service.py`, `pos_service.py`, `balance_sheet_service.py`).
- **Audit trail**: pola `ProductAuditLog` (JSON `changed_fields` + `note` + `changed_time`) dipakai ulang untuk mencatat riwayat perubahan harga di Epic D — jangan buat mekanisme audit baru.

## Aturan Kerja per Sesi

- Selalu gunakan plan mode dulu untuk epic besar (B, F) sebelum menulis kode.
- Setiap epic dikerjakan di sesi/task terpisah — jangan digabung dalam satu sesi.
- Untuk fitur yang menyentuh angka jurnal/HPP/pajak, tulis test acceptance criteria dulu sebelum implementasi (contoh: total debet = total kredit per batch posting, Aset = Kewajiban + Ekuitas di Neraca).
- Sebelum menghapus kode lama (`get_income_statement`, `get_cash_flow`), wajib ada sanity-check yang membandingkan output lama vs baru pada dataset yang sama — baru hapus setelah cocok.
